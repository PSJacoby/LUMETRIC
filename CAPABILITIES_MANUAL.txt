OVERVIEW
--------
The LUMETRIC acquisition system is a Micro-Manager BeanShell script for
automated time-lapse fluorescence microscopy with real-time ROI analysis,
graphical visualization, and event-driven control. It supports both
hardware-triggered (Arduino) and software-controlled acquisition modes.

Main script: LUMETRIC.bsh (~6900 lines)


ACQUISITION MODES
-----------------

1. SNAP MODE (Software-Controlled)
   Configuration: USE_CIRCULAR_BUFFER = false  (or USE_SIMPLE_SNAP_MODE = true)

   How it works:
   - Script captures frames on-demand using mm.live().snap()
   - Software controls timing and channel switching
   - No Arduino hardware trigger involved

   Hardware requirements:
   - Any compatible camera (demo or real)
   - Standard Micro-Manager setup
   - No Arduino required

   Best for:
   - Testing and development
   - Demo camera setups
   - Single-channel acquisitions
   - When software timing is sufficient (most biological imaging)

   Performance:
   - Timing accuracy: ~10-50 ms (software overhead)
   - Frame rate: Up to 10-20 fps depending on camera and processing


2. CIRCULAR BUFFER MODE (Hardware-Triggered via Arduino)
   Configuration: USE_CIRCULAR_BUFFER = true  (and USE_SIMPLE_SNAP_MODE = false)

   How it works:
   - Micro-Manager pre-allocates large memory buffer (75% of heap)
   - BeanShell uploads the acquisition table to Arduino (serial command 60),
     then sends the start command (serial command 61)
   - Arduino controls all timing: sends TTL trigger to camera, fires LEDs
     for each frame according to the uploaded table
   - Camera captures frames to buffer at hardware-precise intervals
   - Script reads frames from buffer in parallel for ROI processing and saving

   Hardware requirements:
   - Real camera with external trigger support
   - Arduino Giga R1 (or compatible) running LUMETRIC_ArdFirmware
   - Camera TTL trigger wired to Arduino Port J bit 0 (camera trigger output)
   - Camera feedback (shutter open) wired to Arduino CAM_FEEDBACK_PIN
   - LED channels wired to Arduino Port J bits 1-5

   Best for:
   - High-speed acquisitions
   - Precise timing requirements (sub-millisecond accuracy)
   - Multi-channel synchronized imaging with LED control
   - Long experiments with many frames
   - Photoswitching / RESOLFT protocols

   Performance:
   - Timing accuracy: Hardware-limited (typically <1 ms)
   - Frame rate: Camera-limited (tested up to 100 fps)
   - Buffer capacity: ~6000 frames @ 512x512 (3 GB buffer)


ACQUISITION TABLE
-----------------

Each row in the acquisition sequence table defines one step. Up to 32 rows
supported (Arduino firmware limit MAX_ACQ_ROWS = 32).

Columns:
  Channel        LED channel name(s), comma-separated (e.g. "488nm" or "405nm,488nm")
                 In circular buffer mode, maps to Port J LED bits via config pin
                 assignments. Leave empty for photoswitching rows (see below).

  Exposure [ms]  LED on-time and camera exposure duration in milliseconds.
                 Set to 0 for a photoswitching row (no camera trigger; see below).

  Interval [ms]  Full frame period including exposure and inter-frame gap.
                 Must be >= Exposure. Timer starts at the beginning of each frame.

  Frames         Number of frames to capture (0 = run until loop ends or quit).

  Loop Goto      Row number to jump back to when frames are exhausted (0 = no loop).

  Loop Times     Number of loop repetitions (0 = infinite).

  Constant Illum LED channel(s) to hold on during the inter-frame gap
                 (comma-separated channel names). These LEDs fire simultaneously
                 with the camera trigger at the start of exposure, and remain on
                 during the gap until the next frame. The camera trigger bit is
                 never included (BeanShell masks it automatically).
                 Leave empty to turn off all LEDs during the gap.

  Loop Switch Goto  Row number to jump to when the Loop Switch button is pressed
                    during acquisition (0 = disabled for this row).


PHOTOSWITCHING ROWS (Exposure = 0)
-----------------------------------
Setting Exposure [ms] = 0 creates a photoswitching row:
  - No camera trigger is generated
  - No camera feedback wait
  - The Constant Illum pattern is applied to the LEDs immediately
  - The Arduino waits for the full Interval [ms] duration
  - Useful for illuminating the sample for photoswitching, photoactivation,
    or bleaching steps between imaging steps, without capturing a frame.

Example: Row 1 = Channel empty, 0 ms exposure, 500 ms interval,
                 Constant Illum = "405nm"
         ??? pulses 405nm LED for 500 ms, no image captured (photoswitch)
         Row 2 = Channel "488nm", 50 ms exposure, 1000 ms interval
         ??? images the result with 488nm


FRAME TIMING (Circular Buffer Mode)
-------------------------------------
The frame interval timer starts at the beginning of each frame:

  [t = 0 ms]       Camera trigger + Constant Illum LEDs fired simultaneously
  [t ~ 0]          Wait for camera feedback pin (shutter open signal)
  [after feedback] Full channel pinPattern applied (exposure LEDs on)
  [t = exposureMs] Channel LEDs off; Constant Illum LEDs remain on
  [t = intervalMs] Next frame begins (or row ends if frames exhausted)

Shutter latency is included in the interval budget, giving accurate
frame-to-frame timing regardless of camera response time.
For exposureMs = 0, steps 1-4 are skipped; only Constant Illum is applied
and the interval timer runs.


ARDUINO SERIAL PROTOCOL (Circular Buffer Mode)
-----------------------------------------------
Communication: 57600 baud, binary

Keep-alive (Micro-Manager internal):
  BeanShell sends byte 40   ??? Arduino replies [40][currentPinStates]
  Arduino handles this transparently during table upload and acquisition.

Command bytes sent by BeanShell:
  60  Load acquisition table
      Payload: [60][nRows][row0...][row1...]...
      Each row = 13 bytes:
        pinPattern     (uint8)   Port J bit pattern (bit0=camera, bits1-5=LEDs)
        exposureMs     (uint16 big-endian)
        intervalMs     (uint16 big-endian)
        frames         (uint16 big-endian)
        loopGoto       (uint8)   1-based row index, 0 = no loop
        loopTimes      (uint16 big-endian)
        constIllum     (uint8)   Port J pattern for gap LEDs (bit0 always 0)
        loopSwitchGoto (uint8)   1-based row index, 0 = disabled

  61  Start acquisition (run uploaded table)

  66  Quit acquisition (Arduino stops all outputs immediately)

  67  Loop-switch (jump to loopSwitchGoto of current row)

Arduino → PC notification bytes:
  67  Switch-event packet sent by Arduino when a LoopSwitchGoto fires.
      Payload: [67][destRow_1based][frameCountHi][frameCountLo]
      BeanShell receives this asynchronously, patches the sequence-row
      assignment of any already-stored data rows, and re-synchronises
      the RowTracker state machine.

ROWTRACKER — Software state machine (BeanShell-side):
  Mirrors the Arduino's acquisition-table sequencing logic exactly.
  Tracks which sequence row is active for every frame without relying on
  serial packets, using the same goto/loop/counter rules as the firmware.
  When a switch-event packet arrives, RowTracker.patch() retroactively
  corrects all three data lists and re-synchronises its state.
  This allows per-row graph filtering to be accurate even across
  loop-switch events.

HUB PAUSE — Serial integrity during acquisition:
  Micro-Manager's Arduino Hub device adapter sends periodic keep-alive
  bytes (byte 40) and responds to shutter/switch events on the same
  serial port that LUMETRIC uses for its binary protocol.  These bytes
  corrupt the LUMETRIC command stream.

  Solution: a custom property "Paused" added to CArduinoHub
  (mmgr_dal_Arduino.dll, compiled from the LUMETRIC fork of
  mmCoreAndDevices).  When set to "1", the Hub monitor thread sleeps
  50 ms per cycle instead of polling, and shutter/switch writes return
  immediately without touching the port.

  LUMETRIC sets Paused=1 before uploading the acquisition table and
  restores Paused=0 after the last frame is processed.  Outside of a
  LUMETRIC acquisition the Hub operates exactly as in a standard
  Micro-Manager installation — full keep-alive, shutter control, and
  switch properties are available as normal.  The custom DLL is a
  drop-in replacement; no other MM configuration changes are required.

PORT J BIT MAPPING (Arduino Giga R1):
  Bit 0 (0x01)  Camera TTL trigger output
  Bit 1 (0x02)  LED channel assigned to pin 1 in config
  Bit 2 (0x04)  LED channel assigned to pin 2 in config
  Bit 3 (0x08)  LED channel assigned to pin 3 in config
  Bit 4 (0x10)  LED channel assigned to pin 4 in config
  Bit 5 (0x20)  LED channel assigned to pin 5 in config

PROCESSING MODES
----------------

Temporal Mode:
  Compares ROI intensities across frames over time.
  Graph types: Intensity, Frame ratio (odd/even frames)
  Each ROI produces one data series per graph.
  Frame selection: every, odd, even, every Nth (with optional offset).

Spatial Mode:
  Compares two halves of the same frame (e.g. dual-view splitimage setup).
  Image is split along a horizontal or vertical axis.
  ROIs are drawn on one half; the system mirrors them to the opposite half.
  Graph types: Intensity (source half only), Split ratio (source / mirror)
  Split ratio variants: Up/Down, Down/Up, Left/Right, Right/Left
  Every frame is processed in spatial mode.

CONFIGURATION OPTIONS
---------------------

Essential Settings:
  USE_CIRCULAR_BUFFER     = true/false   Choose acquisition mode
  USE_SIMPLE_SNAP_MODE    = true/false   Override to snap mode even if buffer enabled
  CAMERA_CONFIG           = <group>      Camera configuration group
  CAMERA_TRIGGER_CONFIG   = <preset>     External trigger mode preset (circular buffer)
  SPECTRAL_1 ... SPECTRAL_N              Channel definitions (name + pin assignment)
  SERIAL_PORT             = <port>       Arduino COM port (circular buffer only)

  Channel pin assignments in config map each named channel to a Port J bit (1-5).
  Pin 1 = bit 1 (0x02), Pin 2 = bit 2 (0x04), ..., Pin 5 = bit 5 (0x20).
  Pin 0 (bit 0) is reserved for the camera trigger ??? do not assign a channel to it.

Acquisition Sequence Constraints:
  - intervalMs must be >= exposureMs (not enforced by firmware; incorrect values
    will cause the interval wait to return immediately)
  - exposureMs = 0 is valid ??? creates a photoswitching row
  - frames = 0 means run until loop counter expires or quit is pressed
  - loopGoto = 0 means no loop; > 0 is 1-based row index
  - constIllum channel names must not include a channel on pin 1
    (BeanShell automatically masks the camera bit: constIllum &= 0xFE)

Live Pictures Checkbox:
  - Controls GUI display only
  - Images are ALWAYS saved regardless of checkbox state
  - Uncheck to reduce GUI overhead during fast acquisitions

TROUBLESHOOTING QUICK REFERENCE
--------------------------------

Acquisition hangs / no frames captured:
  ??? Using demo camera with USE_CIRCULAR_BUFFER = true
  ??? Solution: Set USE_CIRCULAR_BUFFER = false  OR  USE_SIMPLE_SNAP_MODE = true

Buffer overflow warnings:
  ??? Acquisition too fast or processing too slow
  ??? Solution: Increase frame intervals, reduce ROI count, or reduce resolution

Images not being saved:
  ??? Check experiment folder was created (console messages)
  ??? Check available disk space
  ??? Verify console shows "Saved frame X" messages

Arduino not responding:
  ??? Check SERIAL_PORT matches Windows Device Manager COM port
  ??? Verify firmware was uploaded (PlatformIO: Upload task, exit code 0)
  ??? Test serial monitor at 57600 baud

Camera trigger not working (frames not captured):
  ??? Verify pinPattern bit 0 is set for rows with exposure > 0 (automatic if
     Channel field is non-empty)
  ??? Check CAM_FEEDBACK_PIN wiring (camera shutter signal ??? Arduino)
  ??? Confirm camera is in external trigger mode (CAMERA_TRIGGER_CONFIG)

Constant Illum LEDs not behaving correctly:
  ??? Confirm channel name in Constant Illum column matches config exactly
  ??? Verify channel is not assigned to pin 1 (camera pin)
  ??? Check Port J wiring for the expected bit

Photoswitching row does nothing visible:
  ??? Ensure Constant Illum column is set to the desired LED channel.
     With exposure = 0, pinPattern = 0 (no trigger), only constIllum fires.


GETTING STARTED
---------------

Step 1: Choose your mode
   - Testing?      Use config_example.txt (demo camera + snap mode)
   - Lab imaging?  Create custom config (real camera + snap mode)
   - Production?   Use config_RealSetup.txt (real camera + circular buffer)

Step 2: Edit configuration file
   - Set USE_CIRCULAR_BUFFER and USE_SIMPLE_SNAP_MODE appropriately
   - Configure camera settings for your hardware
   - Define channel names and pin assignments
   - Set SERIAL_PORT for Arduino (if using circular buffer)

Step 3: Load and run
   - Open Micro-Manager
   - Run LUMETRIC.bsh
   - Load configuration file (auto-loads last used)
   - Build acquisition sequence in the Acquisition Settings tab
   - Set up visualization in the Data Visualization tab
   - Click "OK - Start Acquisition"

Step 4: Monitor
   - Live view panel (if enabled) shows current frames with ROI overlays
   - Graphs update in real time
   - Press "Event" to mark timestamps on all graphs
   - Press "Loop Switch" to send byte 67 to Arduino (row-jump)
   - Press "Quit Acquisition" to stop, save all data, and export CSVs


ADVANCED FEATURES
-----------------

Photoswitching / RESOLFT Protocols:
  - Use photoswitching rows (exposure = 0) to interleave illumination steps
    between imaging rows without capturing frames
  - Set Constant Illum to the switching laser channel for that row

Multi-Channel Synchronized Imaging:
  - Comma-separate multiple channel names in the Channel column
  - All listed LED bits fire together with the camera trigger
  - Use separate rows for sequential (alternating) channel imaging

Loop Switch for Triggered Experiments:
  - Assign loopSwitchGoto to a recovery or imaging row
  - Press the Loop Switch button (or send byte 67) to jump on demand,
    e.g. to switch from a stimulation sequence to an imaging sequence
  - Arduino sends a [67][row][frameHi][frameLo] notification packet
    whenever the jump fires; BeanShell patches any already-stored data
    rows retroactively and keeps the live graphs consistent

Row-Filtered Live Plotting:
  - Each graph independently selects which sequence row to display
  - In Temporal mode, set "Numerator" to "Row N" (and "Denominator" for
    ratio graphs); only frames tagged with that row number are plotted
  - Row assignment is computed by RowTracker on every frame and
    corrected automatically if a loop-switch event arrives
  - Enables simultaneous display of e.g. Row 1 (imaging) and Row 2
    (photoswitching readout) in separate live graphs during one acquisition

Hub Pause (Serial Integrity):
  - During circular-buffer acquisition, LUMETRIC sets the Arduino-Hub
    "Paused" property to "1" before uploading the table
  - This halts the MM Hub monitor thread, preventing keep-alive bytes
    from corrupting the LUMETRIC binary protocol
  - Paused=0 is restored immediately after acquisition finishes,
    returning the Hub to full standard MM operation
  - Requires the custom mmgr_dal_Arduino.dll (LUMETRIC fork); outside
    of LUMETRIC acquisitions the Hub behaves identically to stock MM


Split Ratio (Dual-View / Ratiometric):
  - Configure Spatial mode with splitAxis and roiSourceRegion in settings
  - Draw ROIs once on the source half; system mirrors them to the opposite half
  - Use "Split ratio" graph type for ratiometric or FRET analysis


POST-PROCESSOR
--------------

Accessible via the "Open Post-Production" button in the Acquisition Settings tab.
Allows refining ROIs and re-exporting corrected data from an already-acquired
experiment folder without repeating the acquisition.

Workflow:
  1. Select an existing experiment folder (must contain AquisitionSettings.csv)
  2. Settings are automatically loaded from AquisitionSettings.csv
  3. Image source is resolved in priority order:
       a) images/ subfolder (Frame_XXXXX.tif files → assembled into one stack)
       b) Image_Stack.tif (single full stack in experiment folder root)
       c) Stack_Row_N.tif files (per-row stacks; each loaded as a separate stack
          with correct per-row timestamps read from the RAW CSV files)
  4. A reference frame is snapped from the loaded stack and shown for ROI drawing
  5. User draws ROIs in the ROI Manager; existing ROI sets can be restored via
     the ROI Manager load function
  6. "Recalculate" re-measures all stack slices with the current ROI set and
     refreshes the live graphs
  7. "Export" saves BG-corrected, BT-corrected, and/or DE-corrected CSVs to a
     new numbered sub-folder next to the original experiment folder

Correction levels available in the Post-Processor:
  - RAW            Always exported
  - BGcorr         Exported when Background Correction is enabled
  - BTcorr         Exported when Bleedthrough Correction is enabled (Spatial only)
  - BTDEcorr       Exported when Direct Excitation correction is enabled (see below)

Direct Excitation (DE) Correction (post-processor only, Spatial mode):
  Subtracts a scaled per-ROI acceptor offset to remove direct excitation
  of the acceptor fluorophore by the donor excitation laser.
  - Requires Bleedthrough Correction to be active
  - User selects a reference stack, from-frame, and to-frame to average
  - The mean BG-corrected acceptor signal over that range is computed per ROI
  - Correction applied: acceptor[i] -= deFactor * meanDirEx[i]
  - deFactor is a scalar set in the post-processor UI
  - The direction (which half is acceptor) follows the same BT direction setting
  - Exported as _BTDEcorr CSV files alongside _BTcorr files


TECHNICAL SPECIFICATIONS
-------------------------

Supported Image Formats:
  - Input: 8-bit (byte), 16-bit (short) grayscale
  - Output: TIFF (uncompressed, Frame_XXXXX.tif)

ROI Types Supported:
  - Any ImageJ ROI type (rectangle, oval, freehand, polygon)

Data Output:
  - Images:      Frame_XXXXX.tif (5-digit zero-padded)
  - Settings:    AquisitionSettings.csv (human-readable)
                 AquisitionSettings_Arduino.csv (pin/byte values)
  - Graph data:  Graph{N}_{type}_{frameFilter}_{corrLevel}.csv
                 Examples:
                   Graph1_Intensity_every_RAW.csv
                   Graph1_Intensity_Row1_RAW.csv
                   Graph1_Intensity_Row1_BGcorr.csv
                   Graph2_Ratio_Row1_div_Row1_RAW.csv
                   Graph2_Ratio_Row1_div_Row1_BGcorr.csv
                   Graph2_Ratio_Row1_div_Row1_BTcorr.csv
                 corrLevel: RAW, BGcorr, BTcorr, BTDEcorr (post-processor only)
  - Events:      EventTimes.csv
  - ROIs:        RoiSet.zip (ImageJ format)

Acquisition Table Limits:
  - Maximum rows:  32 (Arduino firmware MAX_ACQ_ROWS)
  - exposureMs:    0-65535 ms (uint16); 0 = photoswitching row
  - intervalMs:    0-65535 ms (uint16)
  - frames:        0-65535 (uint16); 0 = run until loop end or quit
  - loopTimes:     0-65535 (uint16); 0 = infinite loop

Memory Management:
  - Snap mode: Minimal overhead
  - Circular buffer: 75% heap allocated automatically
  - Recommended JVM heap: 4-8 GB minimum for circular buffer
